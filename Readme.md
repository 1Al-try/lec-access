# Пользователи, группы и права доступа

> Сквозной сценарий лекции: мы администрируем небольшой учебный сервер. На нём
> работают студент `alice`, студент `bob` и сервисный пользователь `webapp`,
> от имени которого крутится веб-приложение. Через всю лекцию мы будем ломать и
> чинить доступ именно этим троим — держите их в голове, в конце будут вопросы.

---

## 0. Зачем вообще права

В Windows вы привыкли, что «программа либо запускается, либо просит админа». В
Linux всё строже и честнее: **у каждого файла есть владелец, группа и набор
разрешений**, и ядро проверяет их при каждом обращении. Это не украшение — на
этом держится вся безопасность системы. Веб-сервер, взломанный через дырку в
коде, сможет натворить ровно столько, сколько ему позволяют права его
пользователя. Поэтому «просто поставить 777, чтобы заработало» — это не решение
проблемы, а создание новой, просто пока незаметной.

Начнём с простого вопроса: кто я вообще такой в системе?

---

## 1. Кто я? UID, GID и имя

Человекочитаемое имя (`alice`) — это для нас. Ядро же оперирует **числами**:
у каждого пользователя есть UID (user id), у каждой группы — GID (group id).

```bash
id                         # хотим узнать, кто мы и в каких группах состоим
```

```
uid=1001(alice) gid=1001(alice) groups=1001(alice),27(sudo),1005(developers)
```

Что это значит по частям:

- `uid=1001(alice)` — наш числовой идентификатор 1001, имя `alice`. Имя — это
  просто ярлык поверх числа.
- `gid=1001(alice)` — наша **основная** группа. Файлы, которые мы создаём,
  по умолчанию получают именно её.
- `groups=...` — все группы, в которых мы состоим. Здесь важное: мы входим в
  `sudo` (сможем повышать привилегии) и в `developers` (GID 1005).

Число `1001` не случайно: обычные пользователи в большинстве дистрибутивов
нумеруются с 1000. А вот у главного администратора номер особенный:

```bash
id root                    # смотрим на суперпользователя
```

```
uid=0(root) gid=0(root) groups=0(root)
```

**`uid=0` — это и есть root.** Не имя «root» делает пользователя всесильным, а
именно нулевой UID. Если вы создадите второго пользователя и вручную пропишете
ему uid=0, он тоже станет всемогущим. Ядро смотрит на число, а не на имя.

## 2. Где это всё хранится

Пользователи не живут в какой-то магической базе — это обычные текстовые файлы.

```bash
grep -E 'alice|webapp' /etc/passwd   # найдём наших двоих в файле пользователей
```

```
alice:x:1001:1001:Alice Student:/home/alice:/bin/bash
webapp:x:1500:1500::/var/lib/webapp:/usr/sbin/nologin
```

Разберём строку `alice` по двоеточиям (это ключевой навык — уметь читать
`/etc/passwd`):

| Поле | Значение | Смысл |
|---|---|---|
| 1 | `alice` | имя |
| 2 | `x` | пароль (буква `x` = «лежит в /etc/shadow», см. ниже) |
| 3 | `1001` | UID |
| 4 | `1001` | GID основной группы |
| 5 | `Alice Student` | комментарий / полное имя |
| 6 | `/home/alice` | домашний каталог |
| 7 | `/bin/bash` | оболочка при входе |

Теперь сравните с `webapp`. Два отличия критичны:

- поле комментария пустое — это служебный аккаунт, живого человека за ним нет;
- последнее поле — **`/usr/sbin/nologin`**, а не `/bin/bash`. Это значит, что
  войти в систему как `webapp` и получить командную строку **нельзя**. Сервисным
  пользователям намеренно запрещают интерактивный вход: если приложение
  взломают, у злоумышленника не будет привычной оболочки.

А пароли? Их в `/etc/passwd` нет (там `x`). Хэши лежат отдельно, в
`/etc/shadow`, который читается только root'ом:

```bash
sudo grep alice /etc/shadow    # заглянем в файл с хэшами паролей
```

```
alice:$6$xyz...$abc...:19700:0:99999:7:::
```

Здесь `$6$` означает алгоритм хэширования (SHA-512), а дальше — сам хэш. Смысл
разделения простой: `/etc/passwd` может читать любой (там нет секретов),
а `/etc/shadow` — только root.

## 3. Читаем права: `ls -l`

Вот команда, вокруг которой крутится половина лекции:

```bash
ls -l /var/lib/webapp/       # смотрим содержимое каталога веб-приложения
```

```
drwxr-xr-x 2 webapp developers 4096 May 10 12:00 static
-rw-r--r-- 1 webapp developers  812 May 10 12:00 config.yml
-rwx------ 1 webapp webapp      455 May 10 12:00 secret.key
```

Возьмём среднюю строку, `config.yml`, и разберём начало — `-rw-r--r--`.
Это 10 символов, читаем их так:

```
 -        rw-        r--        r--
тип     владелец   группа     остальные
```

- **1-й символ — тип.** `-` обычный файл, `d` каталог, `l` символическая ссылка.
  У `static` первый символ `d` — это каталог.
- **Следующие 3 — права владельца** (`webapp`): `rw-` = читать и писать, но не
  исполнять.
- **Следующие 3 — права группы** (`developers`): `r--` = только читать.
- **Последние 3 — права всех остальных**: `r--` = только читать.

Буквы означают:

| Буква | На файле | На каталоге |
|---|---|---|
| `r` | прочитать содержимое | посмотреть **список** имён (`ls`) |
| `w` | изменить содержимое | создавать/удалять файлы внутри |
| `x` | запустить как программу | **войти** в каталог (`cd`), обращаться к файлам по пути |

Запомните последний столбец — на каталогах права работают неинтуитивно, и это
источник большинства ошибок новичков. К этому вернёмся в разделе 6.

Теперь посмотрите на `secret.key`: `-rwx------`. Владелец `webapp` может всё,
а группа и остальные — **вообще ничего** (`---`). Так и должен выглядеть файл с
приватным ключом.

## 4. Восьмеричная запись: откуда берутся числа

Каждая триада `rwx` — это три бита. Их удобно записать одной цифрой:

```
r = 4      w = 2      x = 1
```

Складываем нужные буквы:

- `rwx` = 4+2+1 = **7**
- `rw-` = 4+2+0 = **6**
- `r-x` = 4+0+1 = **5**
- `r--` = 4+0+0 = **4**
- `---` = 0 = **0**

Значит, права `-rw-r--r--` из примера с `config.yml` — это **644**. А
`-rwx------` у `secret.key` — это **700**. Три цифры = владелец, группа,
остальные.

Проверим на живом примере. Создадим файл и посмотрим на него в двух видах:

```bash
touch report.txt             # создаём пустой файл
ls -l report.txt             # смотрим права, которые он получил
```

```
-rw-rw-r-- 1 alice developers 0 May 10 13:20 report.txt
```

`-rw-rw-r--` = 664. Обратите внимание: файл создала `alice`, но группа у файла —
`developers`. Почему не личная группа `alice`? Забегая вперёд — потому что на
каталоге стоял особый бит (setgid), о нём в разделе 7. Пока просто запомните
эту строку: владелец `alice`, группа `developers`, права 664.

## 5. Меняем права: `chmod`

`chmod` умеет два синтаксиса. Сначала **числовой** — задаём права целиком:

```bash
chmod 640 report.txt         # хотим: владелец rw, группа r, остальные ничего
ls -l report.txt             # проверяем результат
```

```
-rw-r----- 1 alice developers 0 May 10 13:20 report.txt
```

Было `664`, стало `640`: у остальных отобрали чтение полностью. Теперь файл
видят только `alice` и участники группы `developers`.

Второй синтаксис — **символьный**, когда нужно точечно добавить или убрать
одно право, не трогая остальные:

```bash
chmod g-r report.txt         # g=группа, минус, r=чтение → убрать чтение у группы
ls -l report.txt
```

```
-rw------- 1 alice developers 0 May 10 13:20 report.txt
```

Синтаксис читается как «кому / что делаем / какое право»:

- **кому:** `u` (user/владелец), `g` (group), `o` (others), `a` (all)
- **что:** `+` добавить, `-` убрать, `=` установить ровно это
- **право:** `r`, `w`, `x`

Пример посложнее — сделать скрипт исполняемым для всех сразу:

```bash
chmod a+x deploy.sh          # a=все, +x=добавить право на исполнение
```

Числовой способ удобен, когда вы задаёте права «с нуля» и точно знаете
желаемый результат. Символьный — когда нужно аккуратно подкрутить одно право.

## 6. Коварство прав на каталогах

Вот здесь ломается интуиция. Продемонстрируем на `bob`. У `bob` есть каталог
`project`, а внутри — файл `notes.txt`, который сам по себе читается всеми:

```bash
ls -ld /home/bob/project           # -d = смотрим на сам каталог, не на содержимое
```

```
drwxr-x--- 3 bob developers 4096 May 10 14:00 /home/bob/project
```

Права каталога — `750`. Теперь `alice` (она в группе `developers`, значит
попадает в среднюю триаду `r-x`) пытается зайти и почитать файл:

```bash
# выполняет alice
cat /home/bob/project/notes.txt    # хотим прочитать файл внутри каталога bob
```

```
-rw-r--r-- notes.txt  →  содержимое читается нормально
```

Работает: у каталога для группы есть `x` (право входить) и `r` (право
смотреть список), а у самого файла — `r` для всех. Всё сходится.

Теперь `bob` решает «закрыть проект» и убирает у группы право входа `x`,
оставив только `r`:

```bash
# выполняет bob
chmod g=r /home/bob/project        # группе оставляем только чтение списка, без x
```

Что теперь может `alice`?

```bash
# выполняет alice
ls /home/bob/project               # пробуем посмотреть список файлов
```

```
notes.txt
```

Список **видно** — право `r` на каталоге осталось. Но:

```bash
# выполняет alice
cat /home/bob/project/notes.txt    # пробуем прочитать файл, как раньше
```

```
cat: /home/bob/project/notes.txt: Permission denied
```

**Отказано** — хотя права самого файла `notes.txt` не менялись и он всё ещё
`r--` для всех! Причина: чтобы обратиться к файлу *по пути*, нужно право `x`
(«войти») на каждом каталоге этого пути. Мы его убрали. Получается парадокс:
имя файла видно (`r`), а сам файл недоступен (нет `x`).

Вывод, который стоит запомнить навсегда: **`r` на каталоге — это про список
имён, `x` — про доступ к содержимому.** Без `x` каталог превращается в
«витрину»: видно, что внутри лежит, но взять нельзя.

## 7. Специальные биты: setuid, setgid, sticky

Обычных `rwx` иногда не хватает. Есть три «надстройки».

### setuid — запуск от имени владельца файла

Классический пример — команда смены пароля:

```bash
ls -l /usr/bin/passwd        # смотрим на программу смены пароля
```

```
-rwsr-xr-x 1 root root 59976 Feb 6 2024 /usr/bin/passwd
```

Видите `s` вместо `x` в правах владельца (`rws`)? Это **setuid**. Он означает:
«кто бы ни запустил эту программу, она выполнится с правами **владельца файла**
(здесь — root)». Зачем? Смена пароля пишет в `/etc/shadow`, а туда можно только
root'у. Setuid позволяет обычной `alice` поменять свой пароль, не давая ей root
насовсем — root получает только сама программа `passwd` на время работы.

### setgid на каталоге — наследование группы

Помните загадку из раздела 4, где файл `alice` получил группу `developers`, а не
`alice`? Вот разгадка:

```bash
ls -ld /home/bob/project     # снова смотрим на каталог проекта
```

```
drwxr-sr-x 3 bob developers 4096 May 10 14:00 /home/bob/project
```

`s` в правах группы (`r-s`) — это **setgid на каталоге**. Правило: все файлы,
созданные внутри такого каталога, автоматически получают группу **каталога**
(`developers`), а не личную группу создателя. Именно поэтому `report.txt` от
`alice` оказался в группе `developers` — он создавался в setgid-каталоге. Это
стандартный приём для общих папок команды: неважно, кто создал файл, — он сразу
принадлежит общей группе, и все её участники имеют к нему доступ.

### sticky bit — защита от удаления чужого

```bash
ls -ld /tmp                  # смотрим на общий каталог для временных файлов
```

```
drwxrwxrwt 10 root root 4096 May 10 15:00 /tmp
```

Последний символ — `t` вместо `x`. Это **sticky bit**. `/tmp` доступен на запись
всем (`rwxrwxrwx` было бы 777), а значит любой мог бы удалить чужие файлы. Sticky
bit меняет правило: **удалить файл в таком каталоге может только владелец файла
(или root)**, даже если у других есть право `w` на каталог. Без него общий `/tmp`
был бы полем для диверсий.

## 8. Становимся кем-то другим: `su` и `sudo`

Иногда обычных прав не хватает и нужно временно стать root. Есть два пути.

`su` — «подменить пользователя» целиком, зная его пароль:

```bash
su - webapp                  # хотим стать пользователем webapp
```

```
This account is currently not available.
```

Не пустило! Помните поле оболочки в `/etc/passwd`? У `webapp` там `nologin`.
Даже root, сделав `su - webapp`, не получит оболочку — служебному пользователю
она запрещена by design.

`sudo` — «выполнить **одну команду** от имени root», вводя **свой собственный**
пароль:

```bash
sudo systemctl restart webapp    # перезапустить сервис от имени root
```

```
[sudo] password for alice:
```

Почему `alice` вообще это позволено? Вспомните `id` из самого начала: она в
группе `sudo`. Кому что разрешено — описано в `/etc/sudoers`. Редактировать его
надо **только** через `visudo` (он проверяет синтаксис перед сохранением; ошибка
в этом файле может закрыть доступ всем):

```bash
sudo visudo                  # безопасно редактируем правила sudo
```

Внутри встречаются такие строки:

```
%sudo   ALL=(ALL:ALL) ALL
webapp  ALL=(root) NOPASSWD: /usr/bin/systemctl restart webapp
```

Читаем:

- `%sudo ALL=(ALL:ALL) ALL` — знак `%` означает **группу**. Любой участник
  группы `sudo` может выполнить любую команду от любого пользователя. Вот почему
  `alice` всесильна через `sudo`.
- Вторая строка — точечное правило: пользователю `webapp` разрешено запускать
  **ровно одну** команду (перезапуск своего сервиса) и **без пароля**
  (`NOPASSWD`). Это и есть **принцип наименьших привилегий**: даём ровно
  столько, сколько нужно для работы, и ни каплей больше.

Сравните это с соблазном «добавить `webapp` в группу `sudo`, чтобы не мучиться».
Разница между этими двумя подходами — это и есть разница между надёжной системой
и системой, которую взломают через её же собственный сервис.

## 9. Почему `chmod 777` — почти всегда ошибка

Теперь у вас есть весь контекст, чтобы понять, что реально делает эта команда:

```bash
chmod 777 /var/lib/webapp/config.yml   # "чтобы наконец заработало"
ls -l /var/lib/webapp/config.yml
```

```
-rwxrwxrwx 1 webapp developers 812 May 10 12:00 config.yml
```

`777` = `rwxrwxrwx` = **читать, писать и исполнять могут вообще все**, включая
любого пользователя и любой процесс на машине. Для конфига веб-приложения это
означает: если злоумышленник получит доступ хоть к какому-нибудь захудалому
аккаунту на сервере, он сможет переписать ваш конфиг (например, подсунуть свой
адрес базы данных). Плюс бит `x` на текстовом конфиге вообще бессмыслен — его
никто не «исполняет».

Почти всегда `chmod 777` — это диагноз: человек не понял, *какому именно*
пользователю или группе не хватает доступа, и «решил» проблему, открыв всё всем.
Правильный путь — понять, кто должен иметь доступ, и выдать минимальные права
именно ему (через владельца, группу и, если нужно, ACL). Что такое ACL — очень
коротко в следующем разделе.

## 10. Когда трёх триад мало: ACL (обзорно)

Классическая модель «владелец / группа / остальные» описывает права только для
**одной** группы. А если нужно, чтобы к файлу имели доступ `alice` и участники
`developers`, но при этом ещё и лично `bob` (который в другой группе)? Тут
выручают ACL — списки доступа.

```bash
setfacl -m u:bob:r /home/alice/report.txt   # дать лично bob право чтения
getfacl /home/alice/report.txt              # посмотреть полный список доступа
```

```
# file: home/alice/report.txt
# owner: alice
# group: developers
user::rw-
user:bob:r--          ← отдельное правило лично для bob
group::r--
mask::r--
other::---
```

Появилась строка `user:bob:r--` — персональное правило поверх обычных прав.
В `ls -l` наличие ACL помечается знаком `+` в конце: `-rw-r-----+`. На этом
уровне достаточно знать, что ACL существуют и решают задачу «дать доступ
конкретному человеку вне общей группы»; детали — тема отдельного занятия.

## Итоги

- В основе всего — **числа**: UID и GID. `uid=0` — это root, имя вторично.
- Пользователи и группы — это обычные файлы: `/etc/passwd`, `/etc/group`,
  `/etc/shadow`.
- Права читаются как `тип + владелец(rwx) + группа(rwx) + остальные(rwx)`,
  а в цифрах `r=4 w=2 x=1`.
- На **каталогах** `r` = список имён, `x` = доступ к содержимому. Это главная
  ловушка.
- Специальные биты: setuid (запуск от владельца), setgid (наследование группы),
  sticky (только владелец удаляет свои файлы).
- Повышение привилегий — через `sudo` с **точечными** правилами, а не раздачей
  всем группы `sudo`. Принцип наименьших привилегий — главный.
- `chmod 777` — не решение, а спрятанная проблема.

Внимание, тонкий момент: сам факт, что владелец файла `webapp`, а права для

1)Да сможет, х означает право войти в каталог CD если у пользователя есть соответствующая права на Фаил.

2)Нет, не пооучится, для просмотра ls требуются права r (католога) без этого система не даст вывести список.

3)В слайде 6 четко сказано: r в каталоге — это (право смотреть списки) , а x —(право входить). Они работают независимо. Если у вас есть только x, вы находитесь в «темной комнате»: вы можете взять конкретную вещь, если знаете, где она лежит, но не можете осмотреться и увидеть, что там вообще есть

2.
1)Будет группа alice

2)Бит setgid (как объясняется в разделе 7) — это свойство каталога, в котором создается файл. Он заставляет новые файлы наследовать группу этого каталога.
Файл "cp report.txt" получил группу developers, потому что был создан внутри каталога /home/bob/project, у которого установлен setgid и группой-владельцем является developers

Когда alice копирует файл к себе домой командой cp report.txt /home/alice/, создается новый файл. Этот новый файл наследует группу не исходного файла, а того каталога, где он создается (то есть /home/alice/).

3.
1) nologin: Запрещает интерактивный вход. Даже если злоумышленник взломает webapp, он не сможет запустить командную оболочку (bash/sh), чтобы свободно исследовать систему.
2) Одиночное правило sudo: Разрешает выполнить ровно одну конкретную команду (перезапуск сервиса) без пароля.
3) Сравнение с группой sudo: Если бы webapp просто добавили в группу sudo, любой, кто получил контроль над приложением, смог бы выполнить sudo bash и мгновенно получить полные права root на всей машине.

Получается- Взлом ограничивается одной командой, а не превращается в полный захват сервера.


4.
Владельцу (webapp) права 777 не дают никаких дополнительных возможностей по сравнению с 700. В обоих случаях у владельца есть полные права rwx. Разницы для самого приложения нет.

Опасность 777 кроется исключительно в последней триаде (права для «остальных»).

При 700 доступ к файлу имел только webapp. При 777 доступ открывается всем пользователям и процессам в системе:

- Чтение (r) — любой может украсть секреты из конфига.
- Запись (w) — любой может подменить настройки.
- Выполнение (x) — хотя для .yml это бессмысленно, сам факт наличия этого права у всех — грубая ошибка.

И как сказано -777= rwxrwxrwx= читать, писать и исполнять могут вообще все , включая любого пользователя и любой процесс на машине
